## 1. 문제의식

### 1.1 정보는 이미 있다. 그러나 흩어져 있고, 내 상황으로 번역되어 있지 않다

호우·강풍·폭염 같은 특보가 발효되면 시민은 아래 정보를 각각 다른 곳에서 만난다.

| 정보 | 어디에 있나 | 형태 |
|---|---|---|
| 기상특보(종류·발효 구역·통보문) | 기상청 | 구역/종류별 현황 |
| 긴급재난문자 | 휴대폰 CBS, 재난안전데이터 | 지역 단위 짧은 문자 |
| 행동요령 | 행정안전부 국민행동요령, 지자체 매뉴얼 | 재난 유형별 긴 문서 |

문제는 **정보의 부재가 아니라 결합의 부재**다.

- 문자는 "무엇이 발효됐는지"는 알려주지만 "그래서 지금 나(예: 반지하 거주, 지금 외출 중)는 뭘 해야 하는지"는 알려주지 않는다.
- 행동요령은 재난 유형별로 일반론이 쓰여 있어, 현재 발효된 특보와 연결해 읽는 일은 사용자 몫이다.
- 특보는 여러 종류가 동시에 걸리고(예: 태풍 = 강풍 + 풍랑 + 호우 + 폭풍해일), 지역 단위(시·군·구/특보구역)도 서로 맞지 않는다.
- 지명이 모호하다("광주" = 광주광역시 / 경기도 광주).

> 주의: 안전디딤돌·국민재난안전포털 등이 행동요령을 이미 제공한다. 본 프로젝트의 문제 정의는 "행동요령이 없다"가 아니라 **"특보·문자·행동요령을 내 위치·상황에 맞게 연결해 주는 층이 없다"**이다.

### 1.2 왜 AI 에이전트인가

- 질문이 자연어다("지금 광주 비 많이 오는데 나가도 돼?"). 의도·재난 유형·지역을 추출해야 한다.
- 필요한 정보가 여러 소스에 흩어져 있어 **조회 계획(plan) → 병렬 조회 → 결합**이 필요하다.
- 결과를 사용자 상황에 맞는 말로 풀어 설명해야 한다.
- 단, **위험 판단 자체는 AI가 하지 않는다.** 판단은 규칙(코드), AI는 이해·계획·설명을 맡는다. (5.3 참조)

### 1.3 이 프로젝트가 하지 않는 것 (비범위)

- 공식 경보를 대체하지 않는다. 모든 화면에 "공식 경보 아님 / 공식 채널 확인" 문구를 상시 표시한다.
- 재난을 예측하지 않는다.
- "안전합니다"라고 말하지 않는다. → "확인된 위험 정보 없음 (기준 시각, 조회 범위)"로만 표현한다.
- 경로 안내/우회로 탐색을 하지 않는다. (경로탐색은 고전 알고리즘 영역이며, 본 프로젝트는 확장 슬롯으로만 남긴다 — 3.4, 5.7)

## 2. 누구에게

### 2.1 주 사용자

**특보·재난문자를 받은 일반 시민.** 재난 전문 지식이 없고, 문자를 받고 당황하거나 대수롭지 않게 넘기는 사람.

### 2.2 대표 상황 (Persona 대신 시나리오)

| # | 상황 | 사용자가 묻는 것 |
|---|---|---|
| S1 | 호우특보 문자를 받았다. 지금 집(저층)에 있다. | "지금 뭘 해야 해?" |
| S2 | 강풍특보인데 곧 외출해야 한다. | "지금 나가도 돼?" |
| S3 | 폭염특보. 부모님(고령)이 혼자 계신다. | "어떤 점을 챙겨야 해?" |
| S4 | "광주 날씨 위험해?" — 어느 광주인지 모호하다. | (시스템이 지역을 올바르게 해석해야 함) |
| S5 | 사용자가 위급한 표현을 쓴다("물이 차오르고 있어"). | (AI 판단 없이 즉시 119/112 안내) |

### 2.3 부 사용자 (프로젝트 평가자)

캡스톤 심사자. 이들에게는 **"안전·신뢰성을 설계로 다룬 에이전트"**라는 점이 드러나야 한다. (6장 평가 설계)

## 3. 어떤 가치를

### 3.1 사용자 가치 (한 문장씩)

1. **한 번에 모아서 본다** — 특보 + 재난문자 + 행동요령을 한 화면에서.
2. **내 위치·상황에 맞춰 읽어준다** — "발효 중" → "그래서 지금 나는 이렇게".
3. **근거를 확인할 수 있다** — 모든 답변에 출처(특보 발표 시각, 문자 원문, 행동요령 문서)를 붙인다.
4. **모르면 모른다고 한다** — 조회 실패는 "안전"이 아니라 "정보 없음".

### 3.2 신뢰·안전 가치 (설계 원칙으로 못 박는다)

| 원칙 | 구현 방향 |
|---|---|
| 판단은 코드, 설명은 LLM | 위험 수준 산출은 규칙 기반. LLM은 결과를 풀어쓰기만 |
| 근거 없는 답변 금지 | 출처 없는 행동요령 문장은 Validator가 차단 |
| 보수적 판단 | 애매하면 낮은 위험이 아니라 높은 쪽/확인 권유 |
| 조회 실패 ≠ 안전 | 소스별 성공/실패를 답변에 명시 |
| 위급 표현은 LLM을 거치지 않는다 | 고정 문구 119/112 안내 |
| 상시 고지 | "공식 경보 아님, 공식 채널 확인" |

### 3.3 프로젝트(학습/포트폴리오) 가치

- 캡스톤 14개 챕터(ADR, FastAPI, MCP, SSE, Multi-Agent, 라우팅, 동적 계획, Validator, 에러 처리, 비용 최적화, 병렬, Stateless, 모듈화, Observability/Eval)를 **자연스럽게 모두 사용**하는 주제.
- 공공데이터 기반 + 약한 사회 문제 + 시연 가능한 결과물.
- "AI가 못하는 것은 코드로, 잘하는 것은 LLM으로"라는 **역할 분담 설계 경험**을 보여준다.

### 3.4 확장 슬롯 (MVP 아님)

도로 돌발·통제(ITS 재난상황정보) 기반 "이동 판단". `[후순위]`
- ITS는 키 하나에 모든 서비스 합산 월 100건, 호출당 1건 응답 → 개발/테스트 불가 수준.
- 따라서 워커 슬롯과 어댑터 스키마만 설계하고, 확보한 요청/응답 1건을 익명화해 fixture로만 보관한다.

## 4. 어떻게 제공할 것인가

### 4.1 제공 형태

웹 챗 UI (React). 사용자가 질문하면 **진행 상황이 스트리밍(SSE)** 으로 보이고, 최종적으로 **판정 카드 + 설명 + 출처**가 표시된다. 라이브 서비스는 불필요하나 "결과물이 눈에 보이는" 시연이 목표다.

### 4.2 시연 방식: 데이터 모드 3종 `[확정]`

| 모드 | 용도 | 비고 |
|---|---|---|
| live | 현재 실제 발효 중인 특보 조회 | 10월 기준 주로 강풍/풍랑 |
| replay | 과거 실제 응답을 저장해 재생 (호우·폭염 등) | **주 시연 방식** |
| synthetic | 사람이 만든 합성 데이터 (엣지 케이스) | 평가·경계 상황용 |

모든 결과 화면에 현재 데이터 모드를 표시한다 (시연이 실제인 척하지 않도록).

### 4.3 시스템 구조 (3분할)

```
[React FE (nginx)]  ←SSE→  [FastAPI + LangGraph (Backend)]  ←MCP→  [MCP Server (별도 컨테이너)]
                                     │                                    ├─ Tool: 기상특보 조회, 재난문자 조회, 지역 해석
                                     └─ LLM (dev: 호스트 Ollama / demo: 호스팅 API)   ├─ Resource: 행동요령 문서
                                                                          └─ Prompt: 답변/설명 템플릿
```

- MCP 서버: 외부 데이터 접근을 캡슐화. 처음엔 stdio, 환경변수로 Streamable HTTP 전환 `[확인 필요: 컨테이너 분리 시 전환 시점]`.
- 백엔드: FastAPI + LangGraph. Stateless 설계(세션 상태는 요청에 포함 또는 최소 저장).
- 프론트: React를 빌드해 nginx로 서빙.
- LLM: `LLM_BASE_URL`, `LLM_MODEL` 환경변수로 교체 가능 (개발=로컬 Qwen, 시연=호스팅 API). 실습과 같이 `fake`(결정론) / `ollama` / 호스팅 API 백엔드를 꽂는 구조로 하고, replay·평가는 `fake`로 돌린다.

폴더 구조 (실습 코드 구조에 맞추되 컨테이너 분리를 반영):

```
mini_project/
├─ backend/      server.py (FastAPI) · agent/ (graph, deps, retry, session_store, mcp_client, *_llm)
├─ mcp_server/   Tool / Resource / Prompt
├─ frontend/     React (또는 단일 HTML) — 시연용
├─ data/         fixtures/ (live·replay·synthetic) · hazard_map · action_guides/
├─ eval/         평가셋 · 실행 스크립트
├─ sh/           setup / run 스크립트
└─ doc/          기획서 · ADR · 매뉴얼
```

실습 폴더(`all_total_vue_student`)는 참고용으로만 두고, 코드를 복사하더라도 뼈대(deps, retry, session_store, SSE 틀)까지만 가져온다.

### 4.4 개발 순서

`fixture·hazard 맵 → MCP 도구 → 그래프(CLI/테스트) → FastAPI + SSE → FE`

- SSE 이벤트 스키마를 초기에 합의하고 FE는 mock 스트림으로 병행 개발 가능.
- **얇은 수직 슬라이스 먼저**: "강풍 특보 지역 브리핑" 한 가지를 끝까지 관통한 뒤 재난 유형을 늘린다.

## 5. 어떻게의 디테일, 무엇을 할 것인가

### 5.1 MVP 범위

| 항목 | MVP |
|---|---|
| 데이터 | 기상특보 + 긴급재난문자 + 행동요령(RAG) |
| 지역 | 데모 지역 1~2곳 (예: 광주광역시 / 경기 광주 — 모호성 시연을 겸함) `[확인 필요]` |
| 재난 유형 | 최소 2개, 목표 3~4개 (호우·강풍·폭염 우선) |
| 입력 | 자연어 질문 + (선택) 브라우저 위치 |
| 비범위 | ITS/경로, 재난 예측, 공식 경보 대체 |

### 5.2 그래프 구조 (LangGraph)

실습 코드(`all_total_vue_student`)의 노드 흐름 `route → plan → gate → research → replan_check → write → validate → finalize`에 맞추고, 재난 도메인 노드를 추가한다.

```
route ─┬─ (위급/범위 외) 고정 응답, LLM 미사용   ← 추가: 위급 표현 분기
       └─ parse_intent(+resolve_location)          ← 추가: 재난 유형·지역 해석
            → plan(LLM) → gate(코드: 지역·유형 확정 여부, 되묻기/가정 칩 판단)
            → research (병렬 workers, 가드+재시도)
                 ├─ 기상특보 worker
                 ├─ 재난문자 worker
                 ├─ 행동요령 RAG worker (LLM 에이전트)
                 └─ [도로 slot, 후순위]
            → replan_check(소스 부족 시 gap task 후 재조사)
            → judge(코드: 위험 수준 판정)              ← 추가: 결정론 판정
            → write(LLM) → validate(근거·금지 표현, 반려 시 재작성) → finalize
```

| 실습 노드 | 본 프로젝트 대응 |
|---|---|
| route | 위급/범위 외/정상 분기 |
| plan | 필요한 소스·hazard 계획 |
| gate | 지역·유형 확정 판단 (실습의 권위 게이트 자리) |
| research | 특보·문자·행동요령 병렬 조회 |
| replan_check | 조회 실패·부족 시 재조사 |
| write / validate | 답변 생성 / 근거 검증 |

- 라우팅: 단일 분기는 `Command`, 병렬 fan-out은 `Send`.
- Supervisor는 라이브러리(langgraph-supervisor)에 의존하지 않고 **직접 구현**한다. 실습 코드도 `StateGraph` 직접 구성이라 그 방식을 따른다 (라이브러리 보관(archive) 가능성 `[확인 필요]`).
- 노드는 `SupervisorDeps`를 `functools.partial`로 주입받는 순수 함수로 작성한다 (실습 방식).
- Worker는 대부분 결정론적 도구 호출 노드. LLM 에이전트는 **행동요령 검색**과 **충돌 해석**에만 사용.
- 상태 저장(checkpointer/thread_id)은 필요한 경우에만.

### 5.3 역할 분담 원칙

| 구분 | 담당 |
|---|---|
| 의도 이해, 계획 수립, 설명 생성 | LLM |
| 지역 해석, 특보 매핑, 위험 수준 판정, 출처 검증 | 코드(결정론) |

포트폴리오 서술에서도 "AI가 위험을 판단한다"라고 쓰지 않는다.

### 5.4 재난 분류 (Hazard)

- `hazard` enum = **기상특보 API 특보코드 ∩ 행동요령 카테고리**.
- `hazard_map`: 특보 종류 ↔ 행동요령 카테고리 ↔ 동의어 표.
- 복수 hazard 허용 (태풍 → 강풍/풍랑/호우/폭풍해일).
- 출력 구조 `HazardParse { intent, hazards[], hazard_source, unmatched[] }`
- 매핑 안 되는 표현은 `unmatched`로 남기고 추측하지 않는다.
- `[확인 필요]` 특보 종류 수가 자료마다 다르다(기상청 11종 vs 포털 12종 표기). 2026년 폭염중대경보·열대야주의보 신설, 특보구역 183→235 개편. **실제 API 응답으로 enum 확정**, 최신 구역코드표 확보.

### 5.5 지역 해석 (`resolve_location`)

1. 후보 열거 — 행정구역 코드 데이터 + Kakao Local.
2. 신호 점수화 — 명시적 수식어(최강) > 대화 이력 > 브라우저 위치(약).
3. 마진 판정 — 차이가 크면 확정, 작으면 가정 칩("광주광역시 기준") 표시 후 답하거나 둘 다 표시.
4. 되묻기는 **답이 크게 다르고 + 긴급하지 않고 + 둘 다 보여주기 비용이 클 때만**.
- 시·군·구 단위만 사용. 위치정보는 최소화(시군구 코드/반올림), 로그·LangSmith에서 마스킹.
- `[확인 필요]` Kakao Local 응답 저장 허용 여부, 법정동/행정동 결과 차이.

### 5.8 Fixture 계획

- 래퍼를 통해 **모든 외부 응답을 저장**하고 호출 카운터 유지 (쿼터 낭비 방지).
- 저장 URL/로그에서 서비스키 제거.
- 구성: 특보 응답(호우·강풍·폭염 각각, 복수 hazard 사례, 해제/빈 응답), 재난문자 샘플, 행동요령 JSON 스냅샷, 지역 후보 사례(광주 등), 실패 응답(타임아웃·빈 값·잘못된 코드).
- 실제 수집 → replay / 손으로 만든 사례 → synthetic 으로 구분 표기.

### 5.9 캡스톤 챕터 매핑

| Query Routing | 위급/범위 외/정상 분기 |

| Validator | 근거·금지 표현·출처 검증 |

### 5.10 평가 설계

**원칙: 놓침(recall) 우선.** 위험을 놓친 사례를 별도 지표로 본다.

| 평가 | 방법 |
|---|---|
| 의도 분류 | 소규모 라벨셋 |
| 재난 유형 분류 | 서울 재난 말뭉치 라벨 → enum 매핑 |
| 행동요령 QA | 정답 문서 ID 일치 |
| 도구 호출 정확도 | 기대 호출 vs 실제 호출 |
| 근거 일치 | 답변 문장 ↔ 출처 문서 |
| 모호 지명 | 약 40건 중 10건 |
| 위급 표현 | 약 5건, 전부 고정 응답이어야 함 |
| 위험 놓침 | 특보 발효 상태인데 "정보 없음/무위험"으로 답한 건수 |

비교 실험(시간 허용 순): Validator on/off(최소) → 병렬 vs 순차 → 라우팅 유무 → 결정론 vs LLM supervisor → 모호성 처리 방식.

Observability: LangSmith 무료 플랜(월 5k 트레이스) 사용, 월 한도 설정, 평가는 샘플링, 위치 정보 마스킹.

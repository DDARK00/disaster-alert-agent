## T-015. stdio MCP 서버 서브프로세스가 부모의 환경변수를 물려받지 않음
- 증상: 셸에서 `DATA_MODE=live`와 `.env`를 export하고 클라이언트를 띄웠는데 서버는 replay 모드로 동작.
- 원인: fastmcp stdio 전송은 서브프로세스 환경을 부모와 같게 넘기지 않는다(`StdioTransport(env=...)`로 명시한 것만 전달). 문자열 경로로 서버를 지정하는 방식은 deprecated 경고도 낸다.
- 조치: 백엔드가 서버를 띄울 때 `StdioTransport(command=..., args=[...], env={"DATA_MODE": ...})`로 명시. 서비스키는 서버가 프로젝트 루트 `.env`를 직접 읽는다(환경변수로 키를 넘기지 않음). 실습 코드(`mcp_client.py`)는 `env={**os.environ}`을 직접 넘기는 방식이라 같은 점에 주의.
- 상태: 해결

## T-014. 특보 발표코드(command)의 의미가 명세에 없어 일부는 가정으로 처리
- 확인된 것: `1` 발표 → 발효, `2` 해제, `7` 변경발표는 강도를 새 값으로 바꿈(실데이터: 폭염 주의보 → 경보(`stress=1`) → 다시 주의보). `3` 연장은 강도 유지로 처리.
- 가정: `6` 정정, `8` 변경해제는 실데이터에 없어 의미를 확인하지 못함 → **보수적으로 "발효 중 + uncertain"** 으로 처리(놓침이 오탐보다 위험). 테스트로 고정.
- 효력 시각: `startTime`(발효), `endTime`(해제)은 `tmFc`(발표 시각)와 다를 수 있음. 예: 08-23 10:00 발표, 11:00 발효. 해제도 발표 후 나중에 효력. `as_of` 시점으로 `active` / `pending_start` / 해제 예고를 구분.
- 실데이터에서 창 시작 직후 첫 이벤트가 `7`(변경발표)로 시작하는 경우가 있음(이전 발표가 조회 창 밖) → 이벤트 하나만으로 상태를 세울 수 있게 처리.
- 상태: 우회(가정 명시)

## T-013. 기상특보 API의 숨은 제약: 조회기간 60일, 오류가 HTTP 200으로 옴
- 증상 1: `fromTmFc=20260101`로 호출하면 HTTP 200인데 `resultCode="99"`, `"최대 조회 기간은 오늘 기준으로 60일 전까지입니다."`. 명세에는 없음(과거 이력이 2004년부터 있다는 소개 문구와 불일치).
- 증상 2: 정상 응답인데 `totalCount`가 0이고 `item`은 6건 들어 있음 → `totalCount`를 신뢰하지 않고 `item` 길이를 사용.
- 증상 3: 상위 구역(`L1130000`, `L1130100`)은 `resultCode="03"`(NO_DATA). 특보는 말단 구역(`광주서부 L1130110`, `광주동부 L1130120`)으로만 발표됨.
- 증상 4: `stnId` 없이 호출하면 전부 `stnId=108`(통합 발표)로 옴.
- 조치: 래퍼가 `resultCode`를 `meta.api_ok`로 기록(HTTP 상태만 믿지 않음). 60일을 넘는 과거는 라이브로 못 가져오므로 **지금 수집해 둔 fixture가 replay 원본**이다. 실제 사례는 2026-08-23~09-03(광주 폭염·열대야·호우)과 2026-10-18(경기 강풍·호우). 이후 더 필요하면 60일이 지나기 전에 추가 수집.
- 상태: 해결(수집 완료), 재수집은 기한 있음

## T-012. 행동요령 API: 필터 없이 호출하면 태풍만 나옴, 페이지 상한 100
- 증상: `safety_cate` 없이 호출하면 `totalCount=61`, 전부 태풍. 지진(01011)은 `totalCount=110`인데 `numOfRows=100`에 100행만 옴.
- 원인: 기본 카테고리가 태풍(01001)이고, 다른 재난은 카테고리 코드를 지정해야 함. 한 번에 100행 상한.
- 조치: `safety_cate=01001~01015`를 순회해 수집(확인된 코드는 `data/hazard_map.json`). 100행 초과 카테고리는 `pageNo`로 이어서 수집.
- 부가: 하위 구조(예보시/특보 중/이후)는 재난마다 이름·개수가 달라 phase 정규화 표가 필요(`hazard_map.json`의 `phases`). `safety_cate3`가 null인 행(문장 제목 행으로 추정)이 카테고리마다 1~4개 섞여 있음 → 사용 전 제외.
- 상태: 해결(수집 방법), 황사(01008) phase 매핑은 미작성

## T-011. 기상특보 API는 "현재 발효 중" 상태가 아니라 발표/해제 이벤트를 준다
- 증상: `getPwnCd`를 오늘 날짜로 호출하면 `command=2`(해제) 2건뿐. 발효 중인지 알려면 이벤트를 시간순으로 접어야 함. `getPwnStatus`의 `t6`(자유 텍스트)는 "o 없음".
- 원인: 이벤트 로그형 API. 날짜 미지정 시 당일 00:00~23:59만 조회.
- 조치: 조회 시작일을 며칠 앞당겨 `(areaCode, warnVar)`별 최신 이벤트를 취하고, 최신이 발표/연장/변경발표이며 `cancel=0`이면 발효 중으로 판정(코드). 이 판정 로직이 `judge` 노드의 핵심 입력이므로 단위 테스트 대상. 과거 호우 사례(10/18)는 replay로 접어 검증.
- 상태: 미해결(설계 반영, 구현 전)

## T-010. 재난문자 `DST_SE_NM`(재해구분) 라벨이 본문과 어긋남
- 증상: 군부대 드론 훈련·안전한국훈련 안내가 `호우`, 불꽃쇼 안내가 `폭염`, 강풍 안내가 `태풍`으로 분류됨. 한 달(10월) 384건 중 `기타`가 159건.
- 영향: 라벨만으로 hazard를 걸러내면 잘못된 문자가 섞이고, 반대로 `기타`로 분류된 진짜 위험이 빠질 수 있음.
- 조치(안): 라벨은 1차 필터로만 쓰고, 본문 키워드(주의보/경보/침수/통제 등)로 2차 확인. 라벨과 기상특보 이벤트가 둘 다 있을 때만 "근거 일치"로 취급. 평가셋에 라벨 오류 사례(드론 훈련 등)를 포함.
- 상태: 미해결(설계 반영)

## T-009. 지역 명칭이 소스마다 다름 (전남광주통합특별시)
- 증상: 재난문자에는 `전남광주통합특별시 신안군`, `전남광주통합특별시 동구`처럼 광주·전남이 통합된 이름이 쓰이고, `rgnNm=광주광역시`로 오늘자 조회하면 0건. 기상청 구역표에는 여전히 `광주광역시`(`L1130000`, 2026-05-31 신설 `L1130100` 등)와 `광주시`(경기, `L1013400`)가 있음.
- 영향: 사용자의 "광주"는 (a) 통합특별시의 광주권 (b) 경기 광주시로 갈리고, 소스마다 지명 키가 달라 이름 비교로는 연결되지 않음.
- 조치(안): 지명 문자열 비교 대신 **정규화 테이블**(소스별 지역 표기 ↔ 내부 지역 ID)을 두고, `resolve_location`이 후보를 내부 ID로 반환. 재난문자는 `rgnNm`을 쓰지 않고 `crtDt`로 넓게 받은 뒤 로컬에서 지역 필터. 시도 단위 문자("부산광역시", "경기도")는 하위 시군구 전체에 적용되는 것으로 처리.
- 상태: 미해결(설계 반영, 정규화 테이블 필요)

## T-008. 한글 폴더 경로가 컴퓨터 연결 도구에서 거부됨
- 증상: `.../실습/capstone` 삭제 권한 요청이 "연결된 폴더가 아니다"로 거부됨. 같은 이유로 `cp ../api_spec/기상청21_*`가 "No such file".
- 원인: macOS 파일명은 자모 분리(NFD)로 저장되고, 직접 입력한 한글은 조합형(NFC)이라 문자열이 다름.
- 조치: 경로는 유니코드 자모로 직접 지정하거나, 한글 이름 대신 `*.docx`, `*21_*` 같은 와일드카드를 사용.
- 상태: 우회

## T-007. 연결 폴더에서 git 커밋 시 임시 파일 삭제 실패
- 증상: `git add` 때 `unable to unlink '.git/objects/xx/tmp_obj_...': Operation not permitted`. `.lock` 파일이 남으면 이후 git이 `File exists`로 실패.
- 원인: 연결 폴더에서는 기본적으로 삭제가 막혀 있음.
- 조치: 세션에서 삭제 권한을 허용한 뒤 남은 `tmp_obj_*`를 정리하고 커밋.
- 예방: 커밋 전에 `find .git -name '*.lock'` 확인. 사용자가 다른 터미널에서 git을 쓰는 중이면 lock을 지우지 않는다.
- 상태: 해결

## T-004. 행동요령에 강풍·풍랑·건조가 독립 항목으로 보이지 않음
- 증상: 재난유형 목록에 "풍수해(태풍, 호우, 대설)", "폭염", "한파", "황사"는 있으나 강풍·풍랑·건조는 없음. 지금(10월) 실제로 발효되는 특보는 주로 강풍·풍랑.
- 영향: 라이브 시연에서 강풍 특보에 연결할 행동요령이 없을 수 있음.
- 결과(2026-10-20 호출): 카테고리 코드를 지정하면 **강풍(01004), 풍랑(01007), 호우(01003), 폭염(01009), 한파(01006), 대설(01005), 황사(01008), 홍수(01002), 해일(01013)** 이 모두 존재. 없는 것은 건조·열대야뿐 → 폴백 불필요, 해당 특보는 "행동요령 없음"으로 명시. 원인은 T-012 (기본 응답이 태풍뿐).
- 상태: 해결

## T-003. 기상특보 명세 내부 불일치
- 증상 1: 요청 예제에 `warninType=6` 오타. 파라미터 표는 `warningType`.
- 증상 2: XML 예제 `resultCode`는 `0`, 응답 명세 표는 `00`.
- 증상 3: 서비스 URL이 `http://` (전송 암호화 없음 표기).
- 호출 결과: JSON 응답의 `resultCode`는 `"00"`, `http://` 호출 성공(HTTPS는 미시험). `tmFc` 등 시각이 JSON에서는 숫자(int), `command`/`cancel`은 문자열, `warnVar`/`warnStress`는 숫자 → 어댑터에서 타입 정규화 필요.
- 조치: 파라미터는 표기준(`warningType`)으로 호출하고 응답이 무시되면 오타 쪽도 시험. `resultCode`는 `0`/`00` 모두 정상으로 처리. HTTPS 가능 여부는 호출로 확인하고, 어떤 경우든 **요청 URL을 로그·fixture에 저장할 때 `serviceKey`를 제거**.
- 상태: 미해결(확인 필요)

## T-002. "광주"가 구역코드 둘 (경기 광주시 / 광주광역시)
- 증상: 구역 xlsx에 `광주`가 `L1013400`(경기 광주시)와 `L1130000`(광주광역시)로 존재. 2026-05-31 신설 코드(`L1130100`, `L1130110`, `L1130120`)도 있음.
- 조치: 이름이 아니라 `areaCode`와 상위 코드(`REG_UP`)로 구분. 과거(replay) 데이터는 개편 전 구역 체계일 수 있어 시점별 매핑 필요.
- 상태: 설계 반영 (구현 전)

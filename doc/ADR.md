# ADR (설계 결정 기록)

형식: 결정 · 이유 · 대안 · 결과. 번호는 결정 순서.

## ADR-001 MCP / 백엔드 / 프론트 3분할
- 결정: MCP 서버, FastAPI+LangGraph 백엔드, 정적 프론트(nginx)를 별도 컨테이너로 분리.
- 이유: 외부 데이터 접근(키·쿼터·스키마)을 한 곳에 가두고, 백엔드는 키를 갖지 않는다. 컨테이너 단위로 교체·테스트 가능.
- 대안: 백엔드의 서브프로세스로 MCP 기동(실습 방식) — 단순하지만 키 분리·독립 배포가 안 됨.
- 결과: 로컬은 stdio, 컨테이너는 Streamable HTTP(`MCP_TRANSPORT=http`). 서비스키는 mcp 컨테이너에만 전달.

## ADR-002 판단은 코드, 설명은 LLM
- 결정: route / gate / judge / validate는 결정론 코드. parse_intent / plan / write만 LLM.
- 이유: 재난 정보에서 LLM 환각은 위험하다. LLM이 실패하거나 엉뚱한 값을 내도 규칙·템플릿으로 떨어진다.
- 결과: LLM 전면 장애에서도 판정·근거·행동요령이 나온다(`test_llm_down_everywhere_...`).

## ADR-003 위험 수준 = 발효 중 특보 등급 그대로
- 결정: 주의보/경보/중대경보를 그대로 쓰고, 재난문자·행동요령은 근거로만 쓴다. 조회 실패는 `unknown`(정보 없음).
- 이유: 설명 가능하고 공식 정보와 어긋나지 않는다. 문자 라벨은 신뢰도가 낮다(T-010).
- 대안: 문자·키워드로 점수화 — 오탐·설명 불가.

## ADR-004 "안전"이라고 말하지 않는다
- 결정: 위험 없음은 "확인된 위험 정보 없음 (기준 시각, 조회 구역)". 조회 실패·범위 밖은 "정보 없음 — 안전하다는 뜻이 아님". 금지 표현은 Validator가 차단.
- 결과: validator → 재작성 1회 → 템플릿 대체. 모든 화면에 "공식 경보 아님" 상시 표시.

## ADR-005 replay / live 모드와 coverage
- 결정: 데이터 모드를 모든 응답에 싣는다. replay는 fixture가 덮는 시간 범위 안에서만 "없음"을 말하고, 밖이면 `no_coverage`.
- 이유: 실제 재난이 없어도 시연하되, 데이터가 없는 것을 위험 없음으로 오해하지 않도록.
- 배경: 기상특보 API는 60일 조회 제한(T-013) → 수집한 fixture가 원본.

## ADR-006 지역은 내부 ID로 정규화
- 결정: 기상청 구역코드·재난문자 표기·사용자 표현을 `data/regions.json`의 내부 ID로 묶는다. 모호하면 되묻지 않고 후보를 모두 조회(위급이면 고정 안내).
- 이유: "광주" 모호성과 `전남광주통합특별시` 표기 변경(T-009).

## ADR-007 Supervisor 직접 구현, 이벤트는 emit 콜백
- 결정: `StateGraph`를 직접 구성(실습 방식). 스트리밍 이벤트는 `config["configurable"]["emit"]` 큐로 전달.
- 이유: langgraph-supervisor 라이브러리 의존 회피, Python 3.10 호환(T-016).

## ADR-008 validate-then-stream
- 결정: SSE로 단계 이벤트와 판정 카드를 먼저 보내고, 검증을 통과한 답변만 `token`으로 스트리밍.
- 이유: 검증 전 토큰을 흘리면 금지 표현이 사용자에게 이미 보인다.
- 대안: 토큰 즉시 스트리밍 + 사후 정정 — 안전 기준에 맞지 않음.

## ADR-009 ITS 도로·경로는 MVP 제외
- 결정: 어댑터 슬롯만 설계. 월 100건·건당 1건 응답으로 개발·테스트 불가(T-001).

## ADR-010 LLM은 환경변수로 교체
- 결정: `LLM_BACKEND` / `LLM_BASE_URL` / `LLM_MODEL`. 개발은 호스트 Ollama(Qwen3 계열), 시연은 OpenAI 호환 API.
- 결과: 모델 이름 변경에 코드 변경 없음. 모델 출력은 항상 `extract_json` + 허용 목록 검증을 거친다.

## ADR-011 카카오맵은 저장 없이 라이브 호출 + 링크 연결
- 배경: Kakao 운영정책이 데이터의 전체·일부를 별도 DB로 저장해 POI 검색 서비스를 구축하는 것을 금지하고, 대량 저장 유료 계약도 제공하지 않음. 장소 ID 기반 라이브 호출과 카카오맵 랜딩 링크 연결을 권고.
- 결정: 요청 시 Kakao Local 라이브 호출, 결과는 저장하지 않고 행정구역·장소 ID·링크만 사용. 경로는 계산·판단하지 않고 길찾기 링크로 넘기기까지만. 지도 SDK 임베드·경로선은 제외. 키는 mcp 컨테이너에만.
- 결과: fixture/replay를 쓸 수 없으므로 테스트는 mock, 실호출은 선택 스모크. 트레이스에는 요약값만 기록.
- 대안: 지도 위젯 임베드 + 경로 표시 — JS 키 노출, 안전 보장으로 오해될 위험 때문에 제외.

## ADR-012 설정·프롬프트·규칙 사전을 파일로 모음
- 결정: `config/settings.py`, `config/rules.yaml`, `prompts/`로 분리. 판정 로직은 코드에 유지하고 데이터(이름·순위·라벨·문구)만 파일로.
- 이유: 환경변수 읽기와 문구가 여러 모듈에 흩어져 안전 문구가 어긋날 위험, 평가 시 프롬프트 변경 추적 어려움.
- 제약: 동작 변경 없이 기존 테스트가 그대로 통과해야 함. 검증기 규칙은 느슨해지지 않는다.

## ADR-013 데이터 소스는 레지스트리(`data/sources.yaml`)로 관리하고 어댑터로 정규화
- 배경: 행동요령 계열 API가 자연재난 1개에서 사회재난·생활안전·민방위로 늘고(활용신청 중), 통합대피소 등 후보도 추가됨. 소스마다 코드를 고치면 안전 규칙과 출처 표시가 어긋난다.
- 결정:
  1. `data/sources.yaml`에 소스마다 한 항목: 이름, 공공데이터포털 번호, 엔드포인트, 환경변수 키 이름, 이용허락범위와 확인 날짜, 출처 표기 문구, 카테고리 코드·페이지 크기, 캐시 전략, **사용 상태**(`active` / `evaluating` / `blocked`). 이 파일이 소스 출처·이용조건의 단일 기준이다.
  2. 같은 형식(safetydata 행동요령 계열)은 `guide` 어댑터 하나가 소스 이름만 바꿔 호출하고 공통 스키마로 정규화한다. 응답 필드는 승인 후 실제 응답으로 확인하기 전까지 추정이다.
  3. 재난 유형 → 조회 소스 선택은 `hazard_map.json`의 `source` 필드로 **코드가 정한다**. LLM은 소스를 고르지 않는다.
  4. `[G#]` 인용에 소스(기관·API 이름)를 포함한다.
  5. 키는 소스별 환경변수로 분리하고 mcp 컨테이너에만 주입한다.
  6. 호출 전략은 소스 유형별: 행동요령은 기동 시·일 1회 캐시, 재난문자·기상특보는 요청 시 조회. 페이지가 꽉 차면 다음 페이지를 요청하고 `totalCount`는 믿지 않는다.
- 확인(2026-10-20): 사회재난·생활안전·민방위·통합대피소 API는 이용 제한이 없고, 기상특보 외 safetydata API는 API당 하루 1,000건 한도다. 연결 전 상태는 여전히 `evaluating`, 코드 연결과 검증을 마치면 `active`.
- 규칙: `evaluating` 소스는 서비스 응답에 쓰지 않는다. 이용허락범위가 불명확하면(예: 공공누리 3유형의 변경금지) 확인 전까지 `evaluating`.
- 스크래핑 금지: 명시된 이용허락이 없는 웹페이지(예: 국민재난안전포털 국민행동요령 화면, 하단 "All rights reserved", 공공누리 표시 없음)는 수집하지 않는다. 같은 내용이 API로 제공되는지 확인하고, 없으면 담당부서 문의 결과를 `sources.yaml`에 남긴다.
- 대안: 소스별 개별 모듈 — 안전 문구·출처 표시가 소스마다 달라질 위험.

## ADR-014 조회 실패는 원인 코드로 분류하고 원인별 문구로 말한다
- 배경: 모든 실패가 "조회하지 못했습니다" 하나로 나가 API 오류·키 문제·한도·네트워크·MCP 불가를 사용자도 개발자도 구분할 수 없었다.
- 결정:
  1. `status=failed`에 `cause`를 붙인다. 외부 API 쪽(`mcp_server/failures.py`가 capture 레코드로 판정): `api_auth_error`(키 미설정·미등록, HTTP 401/403, resultCode 20·21·30~33) · `rate_limited`(resultCode 22, 자체 일일 카운터) · `api_http_error` · `api_result_error`(resultCode≠00) · `api_timeout` · `network_error` · `response_invalid`(JSON 아님·잘림·헤더 없음·스키마 불일치). 백엔드 쪽(`mcp_client.mcp_cause`): `mcp_unreachable`(연결 실패) · `mcp_tool_error`(도구 안 예외). LLM 쪽: `llm_unavailable`(답변은 템플릿으로 나가므로 사용자 문구 없음, meta에만).
  2. `no_coverage`(replay 범위 밖)는 실패가 아니므로 `cause`가 없고 별도 문구를 쓴다.
  3. 코드 표·키워드는 `config/rules.yaml`의 `api_errors`(데이터), 문구는 `prompts/messages.yaml`의 `causes.*`. 모든 원인 문구는 "정보 없음" 표준 문장(`answer.gap`, `mcp.*_failed`) 안의 `$reason` 자리에 들어가므로 검증 조각(`no_info`)은 그대로다.
  4. 원인은 판정 `gaps[].cause/reason`, SSE `source` 이벤트, `final.meta.failures`, LangSmith span 메타데이터(`source_failures`), 로그(`mcp.sources`·`backend.agent` 경고 한 줄)에 싣는다. 키·키가 든 URL은 싣지 않는다(capture 마스킹 유지, detail에는 URL을 넣지 않음).
  5. MCP 자체에 연결하지 못하면 지역 해석 전 단계에서 멈추고 고정 응답(`fixed.service_unavailable`, route `unavailable`)을 낸다. 예전에는 요청 전체가 예외로 끝났다.
  6. `/health`에 소스별 최근 live 호출 성공·실패 시각과 원인(`source_health` 도구, 프로세스 메모리), 백엔드→MCP 연결 상태(`mcp_link`)를 노출한다. 사용자 상태가 아니므로 stateless 원칙과 충돌하지 않는다.
- 확인: 잘못된 키로 실제 호출한 응답 모양(T-028)으로 분류 규칙을 정했다. 장애 주입(`eval/faults.py`) 5종이 서로 다른 원인 코드·문구로 나타나는 것을 테스트와 평가 항목으로 고정했다.
- 대안: HTTP 상태만으로 분류 — safetydata는 키 오류도 HTTP 200 + resultCode 30으로 와서 구분이 안 된다.

## ADR-015 행동요령 4종은 한 어댑터로, 일 1회 캐시 + 저장본 폴백, 대상 필터·'데이터에 없음'은 규칙 데이터 + 코드 판정
- 배경: 사회재난·생활안전·민방위 행동요령이 자연재난과 같은 스키마로 확인됐다(doc/API_응답_스키마.md). 시민용이 아닌 행(구조대원 지침)이 섞여 있고, 차량 침수 탈출처럼 자주 묻지만 공식 데이터에 없는 주제가 있다.
- 결정:
  1. `mcp_server/guides.py` 하나가 `data/sources.yaml`의 guide 소스 4종을 같은 코드로 호출·정규화한다. 재난 유형 → (소스, 유형 코드)는 `hazard_map.json`의 `source`·`action_cate2`(코드가 정함, LLM이 고르지 않음). 연결 범위는 작게: 기존 기상 유형 + 지진·화재·산불·정전·교통사고·미세먼지·민방공.
  2. 캐시: live는 프로세스 내 일 1회(KST 날짜 기준), 실패하면 커밋된 fixture로 폴백(`origin=fixture_fallback`, 원인 기록). replay는 fixture만. Redis 등 외부 저장소는 쓰지 않는다(서버 stateless 유지). 호출 수는 기존 일자별 카운터 + 로그 한 줄, `daily_limit`(1,000)에 닿으면 호출하지 않고 `rate_limited`.
  3. 쪽 넘기기: `totalCount`로 쪽 수를 계산하되 꽉 찬 마지막 쪽이면 한 쪽 더 본다(ADR-013 "totalCount를 믿지 않는다" 유지).
  4. 대상 필터: 구조대원·관리자용 단계명·본문 키워드는 `config/rules.yaml` `guide_audience`(데이터), 판정은 `guides.for_citizens`(코드). 걸러 낸 행 수는 응답(`excluded_non_citizen`)에 남긴다.
  5. 공식 데이터에 없는 질문은 `rules.yaml` `not_in_official_data`(단어 묶음 모두 포함)로 코드가 판정 → route `not_in_data`, LLM·도구 없이 고정 "정보 없음 — 해당 항목이 없습니다". 행동요령이 없는 유형(열대야·건조)도 답변에 "해당 항목이 없습니다"를 반드시 쓰게 검증기에 조각(`not_in_data`)을 추가했다(검증 강화).
  6. 외부 응답은 pydantic(`mcp_server/schemas.py`)으로 경계 검증, 실패는 `response_invalid`(ADR-014). LangGraph State는 TypedDict 유지.
  7. `[G#]` 근거에 소스 표시 이름(예: "생활안전 국민행동요령")을 싣고 템플릿·write 사실 데이터에 함께 보인다.
- 대안: 소스별 모듈 — 정규화·필터·출처 표기가 어긋날 위험. 시작 시 전체 수집 — 호출 60여 건을 기동마다 쓰고, replay 재현성이 떨어진다.

## ADR-016 행동요령은 코드가 "지금 할 일 / 미리 대비할 일 / 하지 말 것"으로 묶고, 안전 문구는 의미를 유지한 채 완화
- 배경: 답변이 행동요령을 나열만 해 "그래서 어떻게?"가 보이지 않았고, "이는 안전하다는 뜻이 아닙니다"·"공식 경보가 아닙니다"가 방어적으로 반복됐다(doc/FE_개선_준비.md). 특보구역 코드(L1013400)가 답변·카드에 보였다.
- 결정:
  1. 묶음은 코드(`judge.group_guides`)가 정한다: 본문에 금지 키워드(rules.yaml `guide_groups.dont_words`: 맙시다·마십시오·말아야·지 않습니다·삼가)가 있으면 '하지 말 것', 아니면 단계(cate3 → hazard_map phases)로 during→'지금 할 일', prepare→'미리 대비할 일'. info·after는 넣지 않는다. 묶음별 상한(3/2/2).
  2. 특보가 발효 중이 아닌 유형은 '지금 할 일' 대신 '발생하면 할 일'로 쓰고 '미리 대비할 일'을 먼저 보인다(발효되지 않은 위험을 지금 일처럼 말하지 않기 위해 — 처음 정한 묶음 이름에서 이 한 가지만 바꿈).
  3. 행동요령은 유형당 한 번(모든 단계) 받아 judge가 고른다. LLM(write)에는 묶음 제목과 그 아래 ID를 데이터로 주고 풀어 쓰기만 시킨다.
  4. 문구 완화(의미 유지: 정보 없음 ≠ 안전): 실패는 "위험 여부를 알 수 없으니 공식 채널에서 확인", 위험 정보 없음은 "상황은 수시로 바뀔 수 있으니 공식 채널도 함께 확인", 면책은 "공식 경보를 대신하지 않습니다 · 위급하면 119·112". 검증 조각 `no_guarantee`를 "안전을 보장" → "공식 채널도 함께 확인"으로 바꾸고 기동 검사·Catalog 테스트를 함께 고쳤다. 금지 표현 목록은 그대로.
  5. 특보구역은 `regions.json` `kma_zone_names`(기상청 areaName)로 표시하고 코드는 개발자 상세(툴팁)에만. 답변 문장이 백엔드에서 만들어지므로 백엔드에서 고쳤다(FE는 카드 표시만).
- 대안: LLM이 묶음을 정함 — 같은 행이 실행마다 다른 묶음에 들어가고 검증할 기준이 없다.


## ADR-017 전국 지역 데이터는 특보구역표에서 생성하고, 시도 표기는 신구 명칭 허용 목록으로 맞춘다
- 배경: 지역 데이터가 광주 두 곳(손으로 쓴 `regions.json`)뿐이었다. 기상청 특보구역표(260601)에는 시도급 20·시군 177·세부 권역 103개가 있고, 재난문자는 시도 표기가 소스마다 다르다(강원·전북·제주는 `…특별자치도`, **전라남도 시군은 `전남광주통합특별시 …`와 `전라남도 …`가 섞여 온다** — 재난문자 fixture 실측).
- 결정:
  1. 구역표 xlsx(저장소 밖)에서 뽑은 중간 JSON `data/kma_zones.json`과 생성 입력 `data/region_build.yaml`(시도 허용 목록·광역시 구 목록·특수 구역 연결·줄임말 제외어)로 `mcp_server/tools/gen_regions.py`가 `data/regions.json`을 만든다. 생성본은 커밋하고, 테스트가 `--check`로 최신인지 확인한다. 손으로 쓴 `gwangju_metro`·`gyeonggi_gwangju`는 그대로 두고 그 구역을 덮는 생성 지역은 만들지 않는다(광주 시나리오 불변).
  2. 지역 단위: 광역시(시 전체), 도 소속 시군, 광역시 소속 군(강화·옹진·군위), 독립 특수 구역(울릉군). 특보 구역 = 자기 + 하위 세부 권역 전체(+ 서해5도·흑산도.홍도·추자도·제주도산지·거문도.초도를 해당 시군에 연결).
  3. **도 전체는 지역으로 두지 않는다.** 상위 구역은 특보 이벤트가 없어(NO_DATA, T-013) 조회하면 '위험 없음'으로 잘못 읽힐 수 있다. 도 이름만 오면 시·군을 되묻는다(`fixed.ask_region_province`).
  4. 재난문자·카카오·쉼터 주소 접두어는 시도 허용 목록(신구 명칭 모두) × 시군 이름. 지역 확정은 시군 이름으로 한다.
  5. 해석(`regions.py`): 별칭은 긴 것부터 맞추고 겹치는 짧은 별칭은 세지 않는다. 정식 이름·`시도 + 이름`은 강한 별칭, 줄임말(시·군을 뗀 이름)은 약한 별칭(가정 칩), 일상어와 겹치는 줄임말(진도·강진·양산·고령·음성·동해 등)은 별칭에서 뺀다. 도 이름과 같은 줄임말('제주')은 도로 본다.
  6. 동명(고성군 2곳, 여러 광역시에 있는 중구·동구·서구·남구·북구·강서구)은 **되묻는다**(`fixed.ask_region_candidates`). 단 ADR-006의 '광주' 묶음(`show_both_groups`)은 기존대로 둘 다 조회해 보여 준다 — 시연 동작과 평가 기대값을 바꾸지 않기 위해 데이터로 예외를 둔다.
  7. 광역시의 구 이름은 그 광역시의 별칭(`districts`, 구역표에 구 단위가 없음). 구 이름으로 물으면 답변에 "'○○구' 단위가 아니라 ○○광역시 전체 기준"을 표준 문구(`region.district_scope`)로 밝힌다. 인천은 2026-07 개편 구 이름과 옛 이름을 함께 둔다.
  8. 판정·검증 로직은 바꾸지 않았다. 쉼터 조회 범위(`shelter_area`)는 광주 두 곳에만 있다 — 범위가 없는 지역은 `no_range`로 쉼터 없이 정상 응답(실패 아님).
- 확인: 해석 표(시도/시군/동명/구/신구 표기/일상어) 파라미터 테스트, 실제 재난문자 fixture의 전남 신구 표기가 모두 시군에 매칭되는지, 합성 특보 fixture(임시 폴더)로 광역시 구 질문의 '시 전체 기준' 안내, 평가 5건 추가. 기존 광주 평가는 그대로 통과.
- 한계: replay 특보 원본은 광주 구역(60일)과 전국 3일(10-17~10-19)·당일뿐이라 다른 지역 replay는 대부분 '정보 없음'이고, 전국 3일 창 이전에 발표돼 이어지는 특보는 보이지 않는다(T-034). 시군 별칭 다듬기, 지역별 쉼터 범위, 읍면동 단위는 하지 않았다.
- 대안: 도 전체를 하위 시군 전부 조회(도당 최대 30여 회 호출) — 호출량과 응답 길이 문제로 보류. 이름 충돌을 모두 둘 다 보여 주기 — 후보가 6곳(중구)까지 늘어 되묻기로 정함.

## ADR-018 조회 계획(plan)은 LLM 대신 의도별 규칙 표로 정하고, 행동요령은 RAG 없이 코드가 고른다
- 배경: 계획 LLM의 단계 선택이 의도만으로 정해졌다(T-032: qwen 28건 중 27건). 코드 제약(특보 필수, guide 의도면 행동요령)이 이미 결정의 대부분을 했고, LLM 호출은 요청마다 1.5~2.7초와 비결정성 하나를 더했다.
- 결정:
  1. `config/rules.yaml plan_steps`(데이터): `status → [alerts, messages]`, `guide → [alerts, guide]`, `go_out → [alerts, messages, guide]`. 적용은 `graph.rule_plan`(코드), 특보 조회는 항상 넣고 알 수 없는 의도는 status로 본다. LLM은 parse_intent·write 두 곳만 쓴다.
  2. 규칙으로 정해지지 않던 경우는 `go_out` 하나(qwen 2건 중 1건만 행동요령 포함)였다 → **행동요령을 넣는다**. 외출 판단에는 '하지 말 것' 묶음이 필요하고, 같은 질문에 매번 같은 조회를 하기 위해서다(답변이 조금 길어지는 비용).
  3. 쉼터는 계획과 무관하게 관련 재난(폭염·한파·지진)이면 코드가 붙인다.
  4. `prompts/plan.md`는 비교 스크립트(`eval/compare_plan.py`: 같은 입력에서 LLM 계획 vs 규칙 계획)에만 남긴다.
  5. 행동요령은 RAG(임베딩 검색)를 쓰지 않는다. 공식 행동요령은 4종 합쳐 약 1,500행이고, 재난 유형(hazard_map) → 단계(phases) → 대상 필터 → 묶음(ADR-016)으로 코드가 고르면 충분하며, 고른 행에 `[G#]` ID를 붙여 근거 인용·검증이 쉽다. 기획 단계의 "행동요령 RAG"는 이 결정으로 대체한다.
- 확인: 평가 세트 disaster 41건에서 LLM 계획과 규칙 계획이 40건 같음(다른 1건은 위 go_out). 교체 후 fake 51/51, qwen3:8b 51/51(모든 지표, 템플릿 대체 0), 시나리오 러너 replay 8 + live 1 통과(T-032).
- 결과: 요청당 plan 시간 0(LLM 호출 1회 감소). 체감 응답 시간은 write가 대부분이라 개선 폭이 작다(T-032).
- 대안: LLM 계획 유지 — 결정이 의도와 같아 정보가 늘지 않고 시간·비결정성만 든다. RAG — 행 수가 작고 선택 기준이 명확해 검색 품질 평가·인덱스 관리 비용이 이득보다 크다.

## ADR-019 단계별 표시: 코드가 만든 근거와 검증된 템플릿 요약을 먼저, LLM 답변은 검증 뒤에 교체
- 배경: `judgement`(약 2~5초) 뒤 `final`(검증 통과 후, qwen3:8b 기준 20~45초)이 한꺼번에 와서 대기가 길게 느껴졌다. LLM 토큰을 바로 흘리면 빨라 보이지만 검증 전 문장이 사용자에게 간다(ADR-008 위반).
- 결정:
  1. SSE 순서 `judgement` → `evidence`(코드가 고른 특보·문자·행동요령 묶음·쉼터를 구조화 데이터로) → `quick`(고정 템플릿 요약) → `final`. `quick`은 fallback과 같은 템플릿을 **검증기에 통과시킨 뒤에만** 보낸다.
  2. LLM 답변이 검증을 통과하면 `final`이 요약 영역만 교체한다(근거 카드는 그대로). LLM 실패·검증 반복 실패면 `final.answer`가 `quick`과 같다 — 새 경로를 만들지 않고 기존 fallback을 재사용.
  3. `progress` 이벤트로 짧은 진행 문구(`messages.yaml progress.*`)를 보내고, 조회 실패는 원인별 문구(ADR-014)로 쓴다. 판정·답변 문장이 아니다.
  4. 기존 `token`·`final`은 그대로 둔다(평가·시나리오 러너·외부 소비자 호환).
  5. 화면 표기: 면책은 배너 한 번만(답변의 같은 줄은 배너와 문장이 같을 때만 표시 생략 — 테스트로 문장 일치 고정), 실행 정보는 모델 이름만(`fake`는 "테스트 모드(고정 응답)"), 내부 값(run id, 연결 방식 이름)은 툴팁.
- 확인: 이벤트 순서·`quick` 검증 통과·검증 실패 시 `quick`=최종·LLM 실패·MCP 중단(근거 없음 → `evidence`·`quick` 없음, 원인별 진행 문구)·검증 전 위반 문장이 어떤 이벤트에도 없음을 테스트로 고정. qwen3:8b에서 `quick` 1.7~5.5초.
- 대안: LLM 토큰 스트리밍 — 검증 전 문장 노출. 섹션 단위 생성·검증 — 스트리밍 구조가 크게 바뀌어 보류.

## ADR-020 행동요령 품질: 전용 항목이 없는 열대야는 폭염 계열로 밝혀 쓰고, 필수 행동·중복 제거·보수적 '하지 말 것'·전체 상한은 코드가 정한다
- 배경: 실제 출력에서 열대야주의보 답변의 행동요령이 0줄, 폭염 답변에 같은 말이 두 번(냉방 안 되는 실내, 카페인 음료), "물을 많이 마시고, 카페인 음료는 마시지 않습니다"가 '하지 말 것'에 들어감, 공식 데이터에 있는 열사병 대처요령(119 신고)이 `info` 단계라 빠짐, 개발자 문구("실시간 모드로 확인")와 유형 반복이 사용자에게 보임. 답변이 길어져 qwen write 시간이 늘었다(T-035).
- 결정:
  1. **소스 없는 유형**: `hazard_map.json`에서 `source: null`은 열대야·건조 둘. 열대야는 `guide_from: 폭염`, `shelter: heat` — 기상청 열대야 특보는 더위 특보이고 공식 행동요령에 전용 항목이 없다. 답변에 "열대야 특보는 공식 행동요령에 전용 항목이 없어, 폭염 계열 공식 행동요령을 안내합니다"를 반드시 쓴다(검증 조각 `guide_borrowed` 추가). 폭염과 함께 발효 중이면 한 번만 보인다. **건조는 그대로 '해당 항목이 없습니다'** — 가까운 공식 항목(산불·화재)은 다른 사건(불이 난 뒤)의 행동요령이라 연결을 우리가 추정하게 된다. 이 예외 말고는 ADR-015의 "다른 재난으로 대체하지 않는다"를 유지한다.
  2. **행동요령 0줄 금지**: 받았지만 고를 행이 없으면 gap `unavailable` + "해당 항목이 없습니다"(검증기가 이미 요구하는 표준 문구).
  3. **필수 행동(K4)**: `rules.yaml must_actions`(유형별 단어 묶음, 우선순위 순)에 맞는 행을 단계와 무관하게 '증상이 있으면' 묶음으로 넣는다. 특보 발효 중일 때만. 폭염: 열사병·열경련·울열증 대처요령(증상 설명 행 제외), 한파: 저체온·동상 대처 행. 검증기는 이 행의 인용을 요구한다(강화).
  4. **중복 제거(K2)**: 공백·기호를 뺀 글자 2-gram Dice ≥ `similar_threshold`(0.4)면 같은 행으로 본다. 한 지역 안에서 묶음 순서대로 **먼저 고른 행**을 남기고 다음 후보로 채운다(유형이 달라도 — 태풍·호우 공통 문장). 측정: 폭염 두 쌍 0.44·0.49, 서로 다른 행은 대개 0.2 이하.
  5. **'하지 말 것'(K3)**: 문장·쉼표로 나눈 조각 중 금지 조각이 있고 **권고 조각이 하나도 없을 때만**(`judge.is_prohibition`). 섞인 문장은 쪼개지 않고 단계 묶음(지금 할 일 등)에 둔다. 이유: 섞인 문장을 '하지 말 것' 아래 두면 앞의 권고("물을 많이 마시고")가 금지로 읽힐 수 있고, 반대로 단계 묶음에 두어도 원문의 "마시지 않습니다"는 그대로 남아 금지가 사라지지 않는다 — 오분류 시 해가 적은 쪽. 연결형 금지(`…지 말고`)는 조각 끝에 올 때만 센다("당황하지 않고 대피합니다"는 권고).
  6. **길이 상한(K7)**: 묶음별 상한(`limits`, 한 지역에 유형이 둘 이상이면 `limits_multi`) + 지역 전체 상한 `max_total`(7). 넘치면 필수 행동 > 묶음마다 첫 행(묶음이 통째로 사라지지 않게) > 단계 일치 > 고른 순서로 남기고, 표시는 원래 순서. 원문은 바꾸지 않는다.
  7. **문구(K5)**: `causes.no_coverage` "이 시각의 정보를 확인하지 못했습니다"(replay 여부는 detail에만, no_coverage/failed 구분은 상태로 유지), 조회 범위 이전 발표 "이전에 발표되어 계속 중인 특보 — 정확한 발표 시각은 확인 범위 밖", gap 줄 끝 "위험 여부는 공식 채널에서 확인해 주세요" 제거(맨 끝 면책과 중복, '정보 없음' 표기는 유지), 출처는 행동요령 제목 줄에 한 번, 유형 이름은 한 지역에 유형이 둘 이상일 때만 묶음 제목에, 쉼터 제목은 "공식 목록에 있는 무더위쉼터 일부: …"(유형·소스 표기 제거).
  8. **LLM 출력 정돈**: 검증 전에 내용 없는 구분선(`---`)·줄 끝 공백만 지운다(`compose.tidy_llm`). 모든 내용 줄은 그대로 검증한다. 검증기에 행동요령 묶음 제목 필수를 더했다(강화 — 금지 행이 제목 없이 권고처럼 읽히지 않게).
- 확인: 실제 fixture 행으로 단위 테스트(G7 사례·순수 금지·순수 권고·연결형, 두 중복 쌍, 필수 행동 우선순위·발효 중만, 0줄 표준 문구, 전체 상한), 평가 지표 3개(`no_duplicate`·`group_ok`·`must_action`)와 항목 4건 추가, fake 55/55.
- 대안: 섞인 문장을 절 단위로 쪼개 각 묶음에 — 공식 원문을 바꾸게 되어 인용 무결성이 깨진다. LLM이 묶음·중복을 판단 — 실행마다 달라지고 검증 기준이 없다. 짧은 요약만 쓰게 하는 구조 변경 — 검증기·프롬프트 영향이 커서 보류(로드맵).

## ADR-021 시연용 장애 주입은 환경변수로만 켜고, 백엔드→MCP 경계의 요청 단위 래퍼로 만든다
- 배경: 조회 실패 원인별 "정보 없음" 문구(ADR-014)를 화면에서 보여 주는 시연이 필요하다. 그러나 공개 서비스에 사용자가 장애를 일으킬 수 있는 경로를 두면 안 된다.
- 결정:
  1. `DEMO_FAULTS=1`(기본 꺼짐)일 때만 `/chat`·`/chat/stream`이 `fault`를 받고 `/scenarios`에 장애 시나리오를 보인다. 꺼져 있으면 `fault`가 붙은 요청은 **404**(기능이 없는 것처럼), 알 수 없는 값은 400. README·도커 기본 설정에는 켜지 않는다.
  2. 장애는 요청마다 그래프를 새로 만들어 `FaultGateway`(백엔드→MCP 경계)로 감싼다 — `mcp_down`(연결 실패 → `mcp_unreachable`), `alert_tool_error`(특보 도구만 도구 오류 → `mcp_tool_error`), `shelter_down`(쉼터만). 서버에 상태를 남기지 않고 다음 요청은 정상이다. 원인 분류·문구는 실제 코드 경로 그대로다.
  3. 외부 API 쪽 장애(잘못된 키·resultCode 99·잘린 JSON·시간 초과·한도)는 MCP 프로세스 안의 네트워크 경계라 시연 서버에서는 만들지 않고 `eval/faults.py`(테스트·평가)로만 본다 — 시연용으로 MCP에 장애 스위치를 더하는 것은 공개 경로를 늘린다.
- 확인: 꺼짐(목록 숨김, 두 엔드포인트 404, 일반 요청 정상)·켜짐(3종 원인 코드·문구, 다음 요청 정상) API 테스트, 시나리오 러너 통과.
